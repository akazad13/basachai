BasaChai Technical Design: MVP

The lowest-cost build of the rental MVP: one Linux VPS, no background jobs, no push.

Version 1.3 (MVP) 13 October 2026 Photos: Cloudinary Based on PRD v1.4 Scope: Phase 1, Dhamrai Next: post-MVP design

1Summary and cost

The MVP runs the .NET 10 API and PostgreSQL on one 2 vCPU, 4 GB Linux VPS behind Cloudflare's free plan. Next.js runs on Netlify, and photos are stored and served by Cloudinary's free plan. The estimated running cost is about US$6 to US$46 a month while photo use stays within Cloudinary's free plan.

3Architecture

Cloudflare sends the website to Netlify and the API to the VPS, where Caddy fronts the API and PostgreSQL stays private; photos go to Cloudinary and browsers load them from Cloudinary's CDN.

4Server layout

Three containers share the 4 GB server, with memory caps that leave over 1 GB for the operating system, file cache and upload bursts; no image processing runs on the server.

A 4 GB swap file guards against out-of-memory kills during spikes. Docker's log driver is set to rotate at 10 MB with 5 files per container so logs cannot fill the disk.

7Listing states without background jobs

With no scheduler, expiry is a rule applied whenever a listing is read: a Published listing whose expires_at has passed is treated as Expired everywhere, at once.

  • Effective status. The domain exposes EffectiveStatus(now): if status = published and expires_at <= now, it returns Expired. Public search, detail pages, the owner dashboard and admin views all use it.
  • Public queries also filter on expires_at > now(), so an expired listing leaves search the moment its 30 days run out.
  • Persisting. The stored status is set to Expired, with a history row, the next time anyone writes to that listing or the owner opens their dashboard. Until then the stored value can lag, but nothing displays it.
  • Renew and reconfirm work as in the post-MVP design: they reset last_confirmed_at and set expires_at = now + 30 days.

Moderator hide remains a flag (is_hidden), not a status. Hiding from a report resolves every open report on that listing in the same transaction, and each resolution is audited.

Editing a Live listing keeps it Live with no new review, for now. Each edit writes audit_log with before and after values, so a moderator handling a report can see exactly what changed.

9Search

Search is unchanged from the post-MVP design: one indexed query, AND filters, location trees through ltree, and keyset paging.

SELECT l.*
FROM property_listings l
JOIN locations loc ON loc.id = l.location_id
WHERE l.status = 'published' AND NOT l.is_hidden AND l.purpose = 'rent'
  AND l.expires_at > now()
  AND loc.path <@ @locationPath
  AND l.monthly_rent_bdt BETWEEN @minRent AND @maxRent
  AND l.bedrooms = @bedrooms
  AND (l.last_confirmed_at, l.id) < (@cursorConfirmedAt, @cursorId)
ORDER BY l.last_confirmed_at DESC, l.id DESC
LIMIT @size;   -- at most 24
  • Sorts: confirmed (default), newest, rent_asc, rent_desc. No paid ranking.
  • The "homes found" count is a separate COUNT(*) with the same filters.
  • Location suggest uses trigram similarity on curated aliases, so "Dhamrai", "Dhamray" and "ধামরাই" all match.
  • Public GET responses send Cache-Control: public, s-maxage=60, and a Cloudflare cache rule lets the edge absorb repeat searches.

10Auth and roles

Users sign in with phone number and password. Because the website and API now live on different hosts under one domain, the session cookie is scoped to the parent domain and CORS allows only the website.

  • Cookie. ASP.NET Core Identity cookie with Domain=.{domain}, HttpOnly, Secure, SameSite=Lax, sliding 30 days. Next.js forwards it on server-side calls for signed-in pages.
  • CORS. Only https://www.{domain} is allowed, with credentials. State-changing requests must also carry an antiforgery token in a header.
  • Registration. Bangladeshi mobile format, unique, not verified. At most 5 accounts per IP per day. Passwords of at least 8 characters, checked against a common-password list.
  • Login. 15-minute lockout after 10 failed attempts. Moderators and admins must use TOTP two-factor sign-in, which has no running cost.
  • Password reset. Admin-assisted: support checks identity, an admin issues a single-use 24-hour link, and the action is audited.
  • Roles. Anonymous, Member, Owner (only owners post at launch), Moderator, Admin. An Agent role is reserved but disabled.

Risk: unverified numbers. Anyone can register a number they don't own. Every listing is moderated, numbers are labelled "not verified", reports go to moderators, and an admin can release a number to its real holder.

11Photos

Photos pass through the API to Cloudinary, which stores a re-encoded original and serves resized copies from its CDN; the VPS stores no image files and does no image processing.

Upload

  1. The owner uploads one photo per request (multipart) to POST /owner/listings/{id}/photos: JPEG, PNG or WebP, at most 10 MB, at most 20 per listing.
  2. The API checks ownership, the listing's photo count and the file signature, then streams the file to Cloudinary with the SDK. It does not decode the image itself.
  3. The upload uses a signed preset: resource_type=image, allowed formats jpg, png and webp, folder basachai/{env}/listings/{listingId}, and an incoming transformation that limits the original to 1600 px wide.
  4. The incoming transformation re-encodes the stored original, which drops embedded metadata, including GPS that could reveal the exact address. Confirm in staging that a stored original carries no GPS before launch.
  5. Cloudinary rejects files that are not valid images. On success the API saves the public ID, version, size and dimensions in listing_photos.

Routing uploads through the API, rather than direct browser-to-Cloudinary uploads, keeps every check in one place and leaves no uploaded-but-unregistered files to clean up. The API forwards bytes without decoding them, so the 2 vCPUs are not loaded.

Delivery

  • Pages use three named transformations: card (320 px), detail (768 px) and full (1280 px), each with f_auto,q_auto for the smallest format the browser supports.
  • Strict transformations are enabled, so only these named transformations can be generated. This stops anyone from requesting arbitrary sizes and using up the monthly credits.
  • URLs include the asset version, so a replaced photo gets a new URL and CDN caches never serve a stale image.
  • Next.js uses a Cloudinary image loader with its own image optimization turned off, so Netlify does not bill for resizing.

Delete

Removing a photo deletes its row and calls Cloudinary's destroy in the same request. If the Cloudinary call fails, the row is still removed and the public ID is logged at warning level so an admin can delete it from the Cloudinary console; no cleanup job is needed.

Free-plan budget

Cloudinary meters storage, bandwidth and transformations against a monthly credit allowance. Check the current free-plan allowance and terms before launch. A rough pilot estimate:

12Owner reminders without jobs or push

Owners learn what needs attention when they visit: the dashboard computes reminders from listing data on every load, so nothing has to run in the background.

Newly approvedStatus badge: Published

The site header shows a count from GET /me/attention so a signed-in owner sees it on any page. Owners who never visit simply let listings expire on time, which protects freshness; the PRD's freshness metric shows whether this is enough.

13Contact reveal and analytics

The phone number is never in page HTML; tapping Contact fetches it, and reveals are limited per IP and device in memory.

  • POST /listings/{shortId}/contact needs no login. Starting limits: 10 reveals per hour and 30 per day per IP and device. These are placeholders until the PRD's open item on limits is settled.
  • The client IP is read from CF-Connecting-IP, which the API trusts only because the firewall accepts traffic from Cloudflare's IP ranges alone.
  • Limits reset if the API restarts. That is acceptable for an MVP; Redis fixes it post-MVP.
  • Events (search_performed, listing_viewed, contact_revealed, listing_submitted, listing_published, report_created) are inserted in the same request. search_performed is reported by the browser with its source (home or search). Admin metrics are computed by SQL when the dashboard opens; no nightly rollup.

15Web, SEO and localization

Next.js on Netlify renders public pages on the server, as Netlify Functions, and calls the API through Cloudflare; pages are cached briefly so most visits never reach the VPS.

  • Images. Photo URLs point to Cloudinary's CDN with the named transformations in section 11; Next.js image optimization is off.
  • Routes. /bn/rent/dhaka/dhamrai and /bn/rent/dhaka/dhamrai/2-bedroom-flat-k7f3q2; /en reserved. Pages revalidate every 60 seconds.
  • SEO. Title, description, canonical URL, Open Graph image, and a sitemap built on request from published listings. Unavailable listings show a noindex page with alternatives.
  • Localization. next-intl, Bangla default. Money is stored as whole taka and shown with Intl.NumberFormat('bn-BD', { style: 'currency', currency: 'BDT', maximumFractionDigits: 0 }) (৳২,০০,০০০). Phones are stored as E.164 and validated with ^(?:\+?880|0)1[3-9]\d{8}$. Times are stored in UTC and shown in Asia/Dhaka.
  • Performance. Largest Contentful Paint under 2.5 s on a mid-range Android phone over 4G; API search p95 under 500 ms on the VPS.
  • Accessibility. WCAG 2.2 AA practices.

Every server-rendered page makes a round trip from Netlify's function region to the API, so measure page latency from Bangladesh before launch and lean on the 60-second page cache.

17Testing and deploy

Free CI builds and tests every change; a deploy is one script that pulls the new image, migrates, and restarts the API in seconds.

Every spec with behaviour lists its own test cases and the code that automates them: 101 test cases across 16 specs, plus 7 end-to-end journeys that prove the PRD's acceptance criteria.   • Time. The API takes time from TimeProvider; tests move it forward through /v1/test/clock to exercise read-time expiry and reminders without waiting.

  2. The deploy script connects over SSH, pulls the image, runs the image's migrate command with the migration role (migrations, reference data, the API role's grants), then starts the new API and waits for its health check.
  3. Migrations stay backward compatible so the previous image can be restarted if the new one fails its health check.
  4. Next.js deploys through Netlify's Git-based pipeline, with preview deploys for each pull request.

Staging. To avoid a second server, staging runs as a separate Compose project on the same VPS with smaller limits, used only before releases and stopped afterwards.
