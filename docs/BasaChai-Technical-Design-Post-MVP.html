BasaChai Technical Design: Post-MVP

The next iteration after the MVP: background jobs, push notifications and managed cloud services.

Version 2.0 (post-MVP) 13 October 2026 Based on PRD v1.4 No SMS Scope: after the Dhamrai MVP

This is the post-MVP iteration, not the MVP build. The MVP runs on one low-cost Linux VPS with no background jobs and no push notifications; see BasaChai Technical Design: MVP. Adopt the parts of this design one at a time when the MVP hits the triggers in its "Path to post-MVP" section.

Hosting. The MVP will not be hosted on Azure. The Azure services named here describe one managed target for later scale. Each has an equivalent from other providers or self-hosted (managed PostgreSQL, object storage, Redis, a CDN), so choose the provider when you actually move.

1Summary and stack

After the MVP, BasaChai becomes a server-rendered Next.js site in front of a horizontally scalable .NET 10 API and a job worker, backed by managed PostgreSQL, Redis and object storage behind a global edge.

WebNext.js (App Router), TypeScript, server-side renderingIndexable property pages and fast first load on mobile
APIASP.NET Core on .NET 10 (LTS)Team stack; supported until November 2028
Data accessEF Core with NpgsqlMigrations, LINQ, raw SQL where search needs it
DatabaseAzure Database for PostgreSQL Flexible Server (PostgreSQL 17)pg_trgm and ltree for search and location trees; PostGIS later for maps
JobsHangfire with PostgreSQL storageExpiry, reminders, push sending, retries with a dashboard
NotificationsIn-app notifications + Web Push (VAPID)No SMS or email; no per-message cost
FilesCloudinary paid plan (continuing from the MVP), or Azure Blob Storage + Defender for Storage malware scanningChoose by cost when the MVP outgrows Cloudinary's free plan (section 9)

EdgeAzure Front Door Premium with WAFCDN, TLS, path routing, bot protection
HostingAzure Container AppsScale-to-demand containers without running Kubernetes
ObservabilityOpenTelemetry to Application InsightsTraces, logs and metrics in one place

.NET version. .NET 10 (LTS) is confirmed for both the MVP and this iteration; it is supported until November 2028.

No SMS. Neither the MVP nor this iteration sends SMS. Phone verification stays deferred, password resets stay admin-assisted, and this iteration adds an in-app inbox and browser push for owner reminders.

Library constraints. Moq and AutoMapper are banned. Tests use NSubstitute or hand-written fakes, and mapping is done with explicit extension methods (ToDto(), ToEntity()).

2Architecture

Every request enters through Front Door: pages go to Next.js, /api goes to the .NET API, and photos are served from Blob Storage through the CDN.

ComponentResponsibility
Next.js webPublic pages (home, search, property), owner dashboard, admin dashboard. Renders public pages on the server; calls the API over the internal network.
.NET APIAll business rules: validation, listing state machine, auth, rate limits, moderation, audit. The only component that writes to PostgreSQL, apart from the worker.
WorkerHangfire server: listing expiry, reconfirmation reminders, push sending, photo processing, analytics rollups.
Front DoorTLS termination, WAF and bot rules, CDN caching for pages and photos, path-based routing so cookies stay same-origin.

One .NET solution with four layers and a worker, plus a separate Next.js app, all in one repository.

  • Concurrency on listings uses PostgreSQL xmin as an EF Core row version; conflicting edits return 409.

5Listing state machine

The domain layer allows only the transitions below; any other request returns 409 with code invalid_transition.

Pending reviewPublishedModeratorSets published_at, last_confirmed_at = now, expires_at = now + 30 days; in-app and push notice to owner
Pending reviewChanges requestedModeratorReason required; in-app and push notice to owner
Pending reviewRejectedModeratorReason required; in-app and push notice to owner
Changes requestedPending reviewOwnerSame guards as first submit

PublishedPausedOwnerRemoved from search immediately
PausedPublishedOwnerOnly if expires_at is in the future; otherwise goes to Expired
PublishedRentedOwnerRemoved from search immediately
PublishedExpiredSystemExpiry job when expires_at passes
ExpiredPublishedOwnerRenew: same effect as reconfirm

  • Hide (FR-12) is a flag, not a status: a moderator sets is_hidden on a published listing, and it leaves search without changing the owner's state.
  • Every transition writes listing_availability_history; moderator actions also write moderation_actions and audit_log in the same transaction.
  • Public queries check expires_at > now() as well as status, so a listing disappears on time even if the expiry job is late.

7Search

Search is a single indexed PostgreSQL query: filters combine with AND, a location matches itself and every area beneath it, and results page by keyset for stable ordering.

Parameters

ParameterExampleRule
locationdhamraiSlug; includes descendants via ltree
minRent, maxRent10000, 25000Inclusive, whole taka
bedrooms, bathrooms2Exact match; null values never match
type, furnishing, occupancyflat, anyany or absent means no filter
availableBy2026-12-01available_from is null or on or before the date
qlift parkingFull-text over title, description, amenities
sortconfirmedconfirmed (default), newest, rent_asc, rent_desc
cursor, sizeeyJ..., 20Opaque keyset cursor; size at most 24

Query shape

SELECT l.*
FROM property_listings l
JOIN locations loc ON loc.id = l.location_id
WHERE l.status = 'published' AND NOT l.is_hidden AND l.purpose = 'rent'
  AND l.expires_at > now()
  AND loc.path <@ @locationPath
  AND l.monthly_rent_bdt BETWEEN @minRent AND @maxRent
  AND l.bedrooms = @bedrooms
  AND (l.last_confirmed_at, l.id) < (@cursorConfirmedAt, @cursorId)
ORDER BY l.last_confirmed_at DESC, l.id DESC
LIMIT @size;
  • The result count runs as a separate COUNT(*) with the same filters, so the "homes found" number is always real.
  • The search URL mirrors these parameters, so results are bookmarkable and shareable.
  • Spellings. Location suggest matches location_aliases.normalized with trigram similarity, so "Dhamrai", "Dhamray" and "ধামরাই" resolve to the same place. Aliases are curated, not machine transliterated.
  • Keyword text. PostgreSQL has no Bangla stemmer, so search_vector uses the simple configuration over both scripts.
  • No paid ranking. Sort order uses only freshness or price (PRD section 8).
  • Empty state. With zero results the API returns suggestions (raise budget, widen area); the web app never renders placeholder listings.

8Auth and roles

Users sign in with phone number and password. Nothing is sent to the phone: numbers are not verified at launch, and forgotten passwords are reset with admin help.

Sessions

  • ASP.NET Core Identity issues an HttpOnly, Secure, SameSite=Lax cookie. Front Door serves web and API from one origin, so no tokens live in the browser.
  • State-changing requests require an antiforgery token. Sessions slide for 30 days; changing the password ends other sessions.
  • Moderators and admins must enable TOTP two-factor sign-in.

Registration and recovery

RuleValue
Phone numberValidated for Bangladeshi mobile format and unique, but not verified
PasswordAt least 8 characters; checked against a common-password list
Registration limitAt most 5 accounts per IP per day; WAF bot rules on the endpoint
Login limitLockout for 15 minutes after 10 failed attempts
Forgotten passwordUser contacts support; an admin checks identity and issues a single-use reset link valid for 24 hours. Every issue is audited.

Risk: unverified numbers. Anyone can register with a number they don't own, which can lead to impersonation or number squatting. Mitigations: every listing is moderated, listings show the contact number as "not verified", reports go to moderators, and an admin can release a number to its real holder. phone_verified_at and an IPhoneVerifier interface are kept so verification can be added later without schema changes.

Roles

9Photo pipeline

The MVP stores photos on Cloudinary. When usage outgrows the free plan, either move to a Cloudinary paid plan (no code change) or adopt the self-managed pipeline below, whichever costs less at that volume.

Option A: stay on Cloudinary. Keep the MVP flow (uploads through the API, incoming transformation, named and strict transformations). Optionally switch to direct signed browser uploads to take upload traffic off the API, plus an orphan-cleanup job now that background jobs exist.

Option B: self-managed pipeline. Photos upload straight from the browser to Blob Storage, are scanned for malware, stripped of location metadata, resized, and only then shown. Existing photos are migrated by downloading originals through Cloudinary's Admin API using the stored public IDs.

  1. The web app asks the API for an upload URL. The API returns a write-only SAS for one blob in the incoming container, valid for 10 minutes.
  2. The browser uploads the file directly. Limits: JPEG, PNG or WebP; at most 10 MB; at most 20 photos per listing.
  3. Defender for Storage scans the blob and publishes the result through Event Grid.
  4. The worker checks the file signature, strips EXIF data (including GPS, which could reveal the exact address), and writes 3 WebP sizes (320, 768 and 1280 px wide) to the public container.
  5. The photo's scan_status becomes clean. Infected or invalid files are deleted and marked rejected, and the owner sees why.

Front Door serves the public container under /media with long cache lifetimes; file names contain a content hash, so replaced photos get new URLs.

10Contact reveal and analytics

The advertiser's phone number is never in the page HTML; it is fetched only when a tenant taps Contact, and each reveal is limited and logged.

  • POST /listings/{shortId}/contact returns the number and a tel: link. No login is required.
  • Limits are enforced in Redis per IP and per device cookie. Starting values: 10 reveals per hour and 30 per day. These are placeholders until the exact limits are decided (PRD section 17).
  • Front Door WAF bot rules add a second layer against scrapers.
  • Each reveal writes a contact_events row with hashed IP and device identifiers, never raw IPs.

11Background jobs

Six Hangfire jobs run in the worker; each is idempotent so a retry never sends a duplicate notification or double-expires a listing.

JobScheduleWhat it does
ExpireListingsEvery 15 minutesMoves Published listings past expires_at to Expired; writes history; notifies the owner
ReconfirmRemindersDaily, 10:00 Dhaka timeIn-app and push reminders 3 days before expiry and on the expiry day
SendPushOn demandSends queued Web Push messages with retries; deletes subscriptions that return 404 or 410
ProcessPhotoOn scan resultPipeline step 4 in section 9
CleanupOrphansDailyDeletes unregistered uploads older than 24 hours and expired reset tokens
RollupMetricsNightlyAggregates analytics for the admin dashboard

The Hangfire dashboard is mounted inside the admin area and requires the admin role.

Notifications

  • In-app first. Every notice is written to notifications and shown as a banner and inbox on the owner dashboard, so nothing depends on push being enabled.
  • Web Push. The Next.js app registers a service worker and asks owners for permission after their first listing is submitted, not on first visit. Messages are signed with VAPID keys held in Key Vault.
  • Reach limits. Android Chrome supports push in the browser. On iPhone, Safari delivers web push only after the owner adds BasaChai to the home screen, so the dashboard shows an "Add to Home Screen" prompt on iOS.
  • Safe failure. An owner who never sees a reminder loses nothing but freshness: the listing expires on time and can be renewed from the dashboard.

13Localization

Bangla is the default locale, with every string in message files so English can be added without code changes.

  • Routing. next-intl with locale-prefixed routes: /bn/... (default) and /en/... reserved for later.
  • Data. Locations, property types and amenities have name_bn and name_en. Listing text is stored as the owner typed it.
  • Money. Stored as whole taka in integer. Displayed with Intl.NumberFormat('bn-BD', { style: 'currency', currency: 'BDT', maximumFractionDigits: 0 }), which gives Bangla digits and lakh grouping (৳২,০০,০০০).
  • Phone numbers. Accept 01XXXXXXXXX, 8801XXXXXXXXX or +8801XXXXXXXXX; validate against ^(?:\+?880|0)1[3-9]\d{8}$; store as E.164 (+8801XXXXXXXXX).
  • Time. Stored in UTC; displayed in Asia/Dhaka (UTC+6, no daylight saving).
  • Fonts. Noto Sans Bengali, self-hosted and subset, with font-display: swap.

14SEO and web performance

Public pages are server-rendered with readable URLs, cached at the edge, and kept under the PRD's 2.5-second target on mid-range phones.

Property/bn/rent/dhaka/dhamrai/2-bedroom-flat-k7f3q2SSR; CDN cache 60 s; purged on edit or status change
Static pages/bn/safety, /bn/how-it-worksStatic generation
  • Each property page has a title, meta description, canonical URL and Open Graph image (first photo).
  • A sitemap of published listings and area pages is regenerated hourly.
  • Listings that are no longer published show a "no longer available" page with noindex and nearby alternatives, and drop out of the sitemap.
  • Performance budget. Largest Contentful Paint under 2.5 s on a mid-range Android phone over 4G; API search p95 under 500 ms server time; responsive WebP images with lazy loading below the fold.
  • Accessibility. WCAG 2.2 AA: labelled filters, keyboard-operable dialogs, visible focus, 4.5:1 text contrast.

18CI/CD

Azure Pipelines builds every pull request and promotes the same container images from staging to prod with a manual approval.

  1. Pull request: build, lint, unit and integration tests, vulnerability scan, Bicep what-if.
  2. Main branch: build images, push to Container Registry, build the EF Core migration bundle.
  3. Staging: apply migrations, deploy new revisions, run Playwright smoke tests and the ZAP baseline.
  4. Prod: manual approval, apply migrations, deploy with traffic split (10% then 100%), automatic rollback if health checks fail.

Migrations must be backward compatible with the previous release (expand, then contract) so a rollback never needs a database restore.
